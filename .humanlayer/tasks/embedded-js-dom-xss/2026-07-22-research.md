# Research: Embedded JavaScript and DOM XSS scanning

**Date**: 2026-07-22T13:21:48+02:00

## Research Question

1. How does an HTML or template file move from discovery and language detection through parsing, rule selection, scanning, and finding emission?
2. How do the HTML and template implementations represent inline `<script>` content in tree-sitter, and what is visible to search and taint traversal?
3. How are embedded HTML and JavaScript RON rules loaded, filtered, and converted into `UnifiedRule` behavior?
4. How do the existing frontend and HTML rules model browser-controlled or remote data and DOM XSS sinks?
5. How does the scanner propagate JavaScript taint through values, calls, callbacks, and scopes?
6. How are search and taint findings constructed, deduplicated, and reported?
7. How do prefiltering, eligibility, traversal, and parallel scanning bound HTML/template and JavaScript scanning?
8. What JavaScript DOM-XSS and inline-script behavior is covered by the current test layers?

## Summary

Sighthound discovers files by path, selects an HTML-oriented tree-sitter parser for HTML and Django modes, loads embedded RON rules into one `UnifiedRule` collection, and scans each parsed file through enhanced search and single-file taint passes. Inline scripts are represented as HTML `script_element` nodes and searched as complete HTML-node source ranges; they are not reparsed as JavaScript for the HTML/Django scan path.

The frontend JavaScript rules combine lexical search rules with two source-to-sink taint rules. JavaScript single-file taint is a two-pass variable tracker that records source and propagation information before evaluating sinks. Finding output retains source/sink and trace-related fields, the CLI deduplicates findings, and text, JSON, CSV, and SARIF serializers report the result.

### 2. HTML/template tree-sitter representation and inline scripts

- `HTMLLanguage` and `DjangoTemplateLanguage` both use `tree_sitter_html::LANGUAGE`. HTML search traversal designates `attribute`, `start_tag`, `script_element`, and `element` as call nodes. Its `script_element` function name is the fixed value `"script"`; attribute and tag names use child-node fallbacks for the current grammar. [src/language.rs:525-588](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/language.rs#L525-L588)
- Django mode designates `attribute`, `text`, and `script_element`. Text nodes become pseudo-function names such as `|safe`, `{{`, `{% include`, or `django_template`; a script element again resolves as `"script"`. [src/language.rs:591-660](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/language.rs#L591-L660)
- `traverse_calls_only` recursively walks the parsed tree but yields only adapter-selected call-node types. Search therefore sees an inline script through its enclosing `script_element` and the complete source range of that node. [src/parser.rs:58-99](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/parser.rs#L58-L99)
- The HTML inline DOM-XSS rule uses a `script` eligibility token and pattern matching against the full `script_element` source text. The enhanced search path uses full call-node text when evaluating search patterns. [rules/html/xss.ron:23-47](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/rules/html/xss.ron#L23-L47) [src/scanner/scanning_logic.rs:1815-1903](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/scanning_logic.rs#L1815-L1903)
- Single-file taint collects assignments, calls, declarations, function forms, and template-literal forms. Its no-source-filter collection path does not select HTML `attribute`, `start_tag`, `script_element`, or Django `text` kinds. [src/scanner/scanning_logic.rs:1171-1228](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/scanning_logic.rs#L1171-L1228) [src/scanner/scanning_logic.rs:1513-1592](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/scanning_logic.rs#L1513-L1592)

### 3. Embedded RON rules and `UnifiedRule` contracts

- `Rules` is a single `Vec<UnifiedRule>`. `UnifiedRule` contains search `pattern`/`patterns`, taint `sources`, `sinks`, `propagators`, and `sanitizers`, metadata, file types, and conditions. Its omitted `mode` defaults to `"search"`; the mode accessors use exact `"search"` and `"taint"` values. [src/models.rs:152-281](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/models.rs#L152-L281) [src/models.rs:394-407](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/models.rs#L394-L407)
- Embedded rules are compile-time directories. JavaScript, TypeScript, and TSX load `rules/javascript`; `rules/backend_javascript` is added when a `code_type` is present and differs from `frontend`. HTML and Django load `rules/html`. The loader ignores `exclusion_patterns.ron`, sorts files, deserializes each RON document, then merges their rule vectors. [src/rules.rs:14-29](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/rules.rs#L14-L29) [src/rules.rs:103-172](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/rules.rs#L103-L172)
- A filesystem directory loader merges every `.ron` file, logging and continuing after a deserialization error. `Rules::get_search_rules` and `get_taint_rules` partition only by mode. [src/rules.rs:228-302](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/rules.rs#L228-L302)
- File eligibility tests include patterns first, reject excluded patterns second, and then enforce extensions. The current filter reads `include_patterns`, `exclude_patterns`, and `extensions` from `FileTypes`. [src/scanner/utils.rs:144-190](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/utils.rs#L144-L190)
- Search matching accepts an exact, regex-prefixed, escaped, glob/wildcard, or substring pattern. Taint rules form a mapping for each applicable source/sink pair and select the rule associated with a matching pair. [src/common.rs:10-39](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/common.rs#L10-L39) [src/scanner/taint_utils.rs:15-149](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/taint_utils.rs#L15-L149)

The condition dispatcher recognizes `has_argument`, `in_context`, `has_parent`, `not_literal`, `has_ancestor`, `argument_not_sanitized`, and `has_sibling_pattern`. [src/scanner/conditions.rs:35-65](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/conditions.rs#L35-L65) [src/scanner/taint_utils.rs:203-227](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/taint_utils.rs#L203-L227)

### 5. JavaScript taint state, propagation, and control-flow handling

- The single-file taint scan filters rules by file type, builds a source/sink deduplicator and `VariableFlowTracker`, collects relevant AST nodes, then performs a source-and-propagation pass followed by a sink-finding pass. - Source assignments are recognized from assignment text: the scanner extracts a target, matches the right-hand expression, suppresses an expression containing a configured sanitizer, and records source provenance. [src/scanner/scanning_logic.rs:847-975](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/scanning_logic.rs#L847-L975) [src/scanner/scanning_logic.rs:1231-1323](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/scanning_logic.rs#L1231-L1323)

[src/common.rs:337-379](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/common.rs#L337-L379) [src/common.rs:446-526](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/common.rs#L446-L526)

## Architecture Documentation

The current scan pipeline is:

```text
CLI mode selection
  -> embedded or supplied Rules (UnifiedRule vector)
  -> path discovery and PreFilter
  -> language/path-specific thread-local tree-sitter parser
  -> enhanced search and/or single-file taint traversal
  -> optional cross-file taint stage
  -> Finding vector
  -> CLI deduplication
  -> text / JSON / CSV / SARIF output
```

HTML and Django use the same HTML grammar but expose different call-node sets and template-text naming. The JavaScript frontend rules are selected by file extension and mode; their taint execution uses the shared scanning logic and variable tracker rather than a JavaScript-specific dataflow module. Cross-file analysis is a separate stage gated by filtered file count and code type.
