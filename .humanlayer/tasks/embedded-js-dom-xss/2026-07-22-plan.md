# Embedded JavaScript DOM-XSS Scanning Implementation Plan

## Overview

Add a narrow HTML/template scan phase that reparses only executable inline `<script>` bodies as
JavaScript over the original file bytes, then runs the existing canonical frontend DOM-XSS taint
rule against that tree. Extend the current JavaScript taint source pass at one boundary—promise
fulfillment callbacks—so the scanner detects both held-out flows while retaining exact template
paths and line numbers.

The implementation keeps `html-inline-dom-xss-001` as search-mode fallback coverage. It marks that
fallback with a rule-specific tag so the scanner can exclude non-executable script blocks and prefer
an equivalent source-to-sink taint result without changing the global deduplication key.

## Current State Analysis

HTML and Django files are parsed with `tree_sitter_html`. Search rules see a whole
`script_element`, while the taint traversal cannot see the JavaScript statements inside its
`raw_text` child. The canonical `js-dom-xss-taint-001` rule already owns the source, sink, and
sanitizer policy, but HTML rule loading does not include it and its file-type filter accepts only
JavaScript-shaped paths.

The unified scanner already maps a file once and passes the same source bytes and path through
search and taint analysis. That is the correct seam for a second included-range parse. The
single-file taint engine is a two-pass `VariableFlowTracker`: it records sources/propagation before
matching sinks. Its current function-parameter logic checks parameter names against source tokens;
it does not derive a callback parameter's taint from the promise receiver.

### Key Discoveries

- `tree_sitter_html` exposes each inline body as a `raw_text` child of `script_element`, and a
  `tree_sitter::Range` from that node already uses the original byte offsets and points.
  [src/parser.rs:5-35](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/parser.rs#L5-L35)
  [src/language.rs:525-660](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/language.rs#L525-L660)
- `tree-sitter` 0.26 treats an empty included-range slice as full-document parsing. The cached
  parser must therefore call `set_included_ranges(&[])` after every ranged parse result, including
  parse and range-validation errors.
- The existing thread-local cache owns one primary parser per Rayon worker. A separate JavaScript
  cache avoids switching the primary HTML parser's language or reconstructing a JavaScript parser
  for each template.
  [src/scanner/parser_helper.rs:7-37](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/parser_helper.rs#L7-L37)
- `Rules::load_embedded_rules("html" | "django", ...)` currently loads only `rules/html`.
  `load_all_embedded_rules` appends per-language vectors without deduplicating IDs, so the canonical
  DOM-XSS rule needs targeted deduplication when HTML and JavaScript are both detected.
  [src/rules.rs:103-194](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/rules.rs#L103-L194)
- A JavaScript taint rule can be filtered against a synthetic `.js` applicability path while the
  existing `TaintScanContext.filepath` continues to construct findings from the original template
  path.
  [src/scanner/scanning_logic.rs:1171-1228](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/scanning_logic.rs#L1171-L1228)
- For tree-sitter JavaScript, an inline callback's parent is `arguments`, whose parent is a
  `call_expression`; the callee is a `member_expression` with `object` and `property` fields. The
  first named argument identifies the fulfillment handler, and an arrow's first parameter is
  exposed through either the `parameter` or `parameters` field.
- The default CLI does not merge search and taint findings inside one scanner call. It runs
  `run_simple_analysis`, then `run_taint_analysis_with_verbosity`, appends both vectors, and only
  then invokes the generic deduplicator. Per-file preference is still required for unified library
  callers, but a shared narrow preference helper must also run at this CLI merge point.
  [src/main.rs:104-129](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/main.rs#L104-L129)
  [src/main.rs:226-239](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/main.rs#L226-L239)

  `find_vulnerabilities_unified_with_filters_and_options(..., include_test_fixtures = true)`.
  [src/scanner/vulnerability_scanner.rs:223-289](https://github.com/Corgea/Sighthound/blob/17ddd92d8f8ccded3d812943bdd95b1ab839a353/src/scanner/vulnerability_scanner.rs#L223-L289)
- The two real benchmark inputs and sink lines are:

    (`location.hash` to `document.write`).

## Desired End State

- Default embedded HTML/Django scans load one canonical frontend DOM-XSS taint rule in addition to
  native HTML search rules. Custom file-rule scans receive no hidden rules.
- An HTML/template file with at least one executable inline script gets one additional JavaScript
  parse spanning all eligible body ranges. A file without an eligible range does not request the
  embedded parser.
- Missing/empty `type`, `type="module"`, and recognized JavaScript/ECMAScript MIME types are
  executable. A `src` attribute, empty body, unknown type, JSON/data type, or template type is not.
- Legacy HTML fallback search follows the same executable-script gate, so dangerous-looking text
  inside external, JSON, or template scripts is not reported.
- `location.hash` and `location.search` seed the canonical DOM-XSS rule without a `window.` prefix.
- Only the first callback argument of a `.then(...)` call whose receiver chain matches a configured
  source is seeded. Rejection callbacks, unrelated promises, and suggestive parameter names do not
  create taint.
- The DjangoAt benchmark produces one `cwe-79` taint finding at line 20. The PyGoat benchmark
  produces one at line 42. Both retain the original `.html` path, source/sink evidence, and
  `taint_analysis` / `data_flow` tags.
- When the HTML fallback and embedded taint identify the same file, sink line, and CWE, only the
  taint finding remains. An unmatched fallback or a different-CWE finding on the same line remains.
- The implementation passes the focused unit/integration tests, the standalone JavaScript
  acceptance suite, HTML-only feature compilation, and `make check`.

## What We're NOT Doing

- Building a generic polyglot or tree-sitter injection framework.
- Concatenating scripts into a synthetic buffer or remapping positions after scanning.
- Fetching external scripts or adding cross-file flow between templates and JavaScript files.
- Adding inline event-handler, CSS, server-template encoding, or new DOM sink coverage.
- Loading the full JavaScript rule pack into HTML scans.
- Adding a rule-schema field, dependency, CLI option, persisted state, or feature flag.
- Modeling promise scheduling, rejection propagation, named callback references, or arbitrary async
  graphs beyond inline fulfillment callbacks rooted in configured sources.
- Replacing or broadening `html-inline-dom-xss-001`.
- Refreshing Fusion's vendored Sighthound binaries in this repository change. That remains a
  downstream release step after the Sighthound commit is accepted.

## Implementation Approach

Build the browser-controlled flow as a vertical slice first: parser state safety, executable range
selection, canonical rule loading/partitioning, reporting-path separation, and production scanner
coverage. Then add a source-token-driven promise callback seed to the existing first taint pass.
Finish by applying one shared, rule-tagged precedence operation at both scanner and CLI merge points,
then validate against the exact benchmark files and representative template corpora.

The native and embedded taint slices remain separate. The canonical DOM-XSS rule stays in native
taint only when the discovered file set contains JavaScript/TypeScript; HTML-only loading exposes it
only to the embedded phase. This prevents an HTML-only rule addition from changing Python-oriented
cross-file rule selection while preserving current standalone JavaScript behavior.

#### 1.2 Add a range-safe parser entry point

**File**: `src/parser.rs`

**Changes**: Add `LanguageParser::parse_with_included_ranges`. Attempt the parse only after setting
the ordered ranges, then restore full-document parsing before returning either success or error. A
reset failure must be returned because the parser is cached and cannot safely be reused with unknown
state.

```rust
pub fn parse_with_included_ranges(
    &mut self,
    source: &[u8],
    ranges: &[tree_sitter::Range],
) -> Result<Tree> {
    let parse_result = self
        .parser
        .set_included_ranges(ranges)
        .context("Failed to set included ranges")
        .and_then(|()| self.parser.parse(source, None).context("Failed to parse included ranges"));

    let reset_result = self
        .parser
        .set_included_ranges(&[])
        .context("Failed to reset included ranges");

    match (parse_result, reset_result) {
        (_, Err(reset_error)) => Err(reset_error),
        (result, Ok(())) => result,
    }
}
```

Keep `parse` unchanged as the full-document entry point.

## Phase 2: Propagate Configured Remote Sources Through Fulfillment Callbacks

### Overview

Seed the first parameter of inline `.then(...)` fulfillment handlers when the receiver chain
matches a configured source. Feed that seed into the existing first taint pass so current assignment,
property, call, concatenation, and indexed-access propagation reaches the PyGoat sink.

### Changes Required

#### 2.1 Resolve fulfillment callback source context from the JavaScript AST

**File**: `src/scanner/scanning_logic.rs`

**Changes**:

- Add a helper called only for `arrow_function` and `function_expression` nodes.
- Require the callback's parent to be an `arguments` node and the callback to be its first named
  child. This excludes `.then(success, rejection)`'s rejection handler.
- Require the parent call's callee to be a `member_expression` whose `property` text is exactly
  `then`.
- Match configured source tokens against the callee text (for example,
  `fetch(...).then` or `axios.get(...).then`), which excludes the callback body and avoids
  parameter-name inference.
- Walk only the receiver side of nested `.then` calls to the leftmost non-`then` call. Use that
  root call's starting row and text for source evidence.
- Extract the first callback parameter from the arrow `parameter` field or the first named child of
  `parameters`. Accept simple identifiers only; destructuring and callback references remain out of
  scope.
- Record the parameter with the callback's function context so current function-scope matching
  finds it in descendants.

```rust
fn track_promise_fulfillment_source(
    node: &tree_sitter::Node,
    ctx: &TaintScanContext,
    func_name: &str,
    flow_tracker: &mut VariableFlowTracker,
) {
    let Some((parameter, call, source_root, source_pattern)) =
        Self::promise_fulfillment_source(node, ctx)
    else {
        return;
    };

    flow_tracker.record_tainted_variable(
        parameter,
        TaintVariableInfo {
            source_line: source_root.start_position().row + 1,
            source_pattern,
            source_function: func_name.to_string(),
            assignment_code: crate::parser::get_node_text(&source_root, ctx.source),
        },
    );
}
```

Call this helper in `track_taint_sources_for_node` after existing name-based parameter tracking and
before assignment propagation. Do not modify `VariableFlowTracker`, add a promise graph, or hardcode
`fetch`, `response`, `result`, or `data`.

```rust
#[doc(hidden)]
pub fn prefer_precise_html_dom_xss(findings: &mut Vec<Finding>) {
    let precise = findings
        .iter()
        .filter(|finding| {
            finding.source_info.is_some()
                && finding.sink_info.is_some()
                && finding.tags.as_ref().is_some_and(|tags| {
                    tags.iter().any(|tag| tag == "taint_analysis")
                })
        })
        .map(|finding| (finding.file.clone(), finding.line, finding.cwe_id.clone()))
        .collect::<std::collections::BTreeSet<_>>();

    findings.retain(|finding| {
        let is_fallback = finding.tags.as_ref().is_some_and(|tags| {
            tags.iter().any(|tag| tag == "html-inline-dom-xss-001")
        });
        !is_fallback
            || !precise.contains(&(finding.file.clone(), finding.line, finding.cwe_id.clone()))
    });
}
```

This keeps the preference exact without broadening global deduplication or comparing mutable display
text.
